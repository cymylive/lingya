# Agent Note: 隧道并发锁与主进程脚本语法污染修复

Status: implemented

## Problem
在深度审计中发现了两个隐蔽的致命问题：
1. **/proxy 指令并发冲突**：用户在飞书/QQ 连发两次 /proxy，会触发两次 `tunnel.stopTunnel()` 和 `startTunnelNow()`，由于异步没有加锁，极大概率导致旧的 `cloudflared` 进程未死，新的又启动，产生僵尸进程和端口占用，最终导致隧道彻底瘫痪。
2. **正则替换的语法污染**：在修复并发锁时，试图用正则直接替换 Node 文件。由于沙箱或编辑器自动加入了行号（如 `14: let xxx`），导致主进程出现重复声明、缩进错乱甚至 `SyntaxError`，直接引发 Electron 崩溃。

## Decision
1. **并发锁（Mutex）**：在 `remote-ipc.js` 中引入 `isRestartingTunnel` 标志位。在 `startTunnelNow()` 的首行做判断，如果为 `true` 直接返回「正在重启」，并用 `try...finally` 包裹真正的启动逻辑，确保无论成败都能正确释放锁。
2. **放弃正则，全量重写**：对于被行号污染的主进程文件，绝不再用正则去清理，而是直接读取原文件的纯净逻辑，用 `HCCK2T` (Write) 重新生成一份完全无污染、格式规范的纯代码替换掉它。
3. **防范死锁**：重启前强制确保旧进程已经释放了全局状态。

## Alternatives considered
- **把 `/proxy` 的防抖交给前端（PWA）处理**：治标不治本，用户如果在通信平台连发两次，依然会打到后端。后端加锁才是唯一可靠防线。
- **用 ESLint 自动修复被污染的文件**：在代码已经出现语法级错误（如重复声明）时，ESLint 也可能无法正确解析，重写是最快最稳的。

## Consequences
- 无论怎么狂点重启隧道指令，服务器都不会产生孤儿进程。
- 主进程的稳定性大幅提升，排除了潜在的启动崩溃隐患。
