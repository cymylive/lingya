# Agent Note: 彻底移除移动端自动跟随滚动的决断

Status: implemented

## Problem
尽管之前引入了 `isUserScrolling` 锁来防止用户阅读历史时被强制拽回底部，但在实测中，只要有新消息产生（包括流式气泡创建、工具卡片插入），屏幕依然会被拽到底部。
根因在于：代码中多处直接写死了 `scrollToBottom(true)`。这里的 `true` 参数代表“无视所有锁定条件，强制滚到底”。这种底层强制力打破了前端的控制逻辑，且移动端的流式高频刷新极易与惯性滑动冲突，导致体验极其割裂，用户完全失去了浏览历史的权利。

## Decision
采用**“彻底剥夺特权，完全由用户接管”**的极端策略：
1. **清理强制调用**：全面排查并移除了 `ensureStreamEl` 和 `addToolCard` 等函数中所有的 `scrollToBottom(true)`。
2. **状态降级**：AI 正常流式输出、弹工具卡片、产生系统提示时，只触发新消息红点徽章（`elScrollBadge`），绝对不允许操作 `scrollTop`。
3. **白名单机制**：仅保留两个允许自动滚动的场景：
   - 用户自己点击“发送”按钮时（因为用户需要看到自己发的话）。
   - 用户主动点击右下角的“回到底部”箭头时。
4. **移除锁依赖**：既然所有自动滚动都被物理切除，之前为了拦截滚动而维护的 `isUserScrolling` 逻辑也随之退役，代码更加精简。

## Alternatives considered
- **继续完善 isUserScrolling 锁**：治标不治本，只要代码里还有 `scrollToBottom(true)`，总会在某个意想不到的代码分支（如插入工具卡片）绕过拦截。
- **给用户提供一个“锁定/解锁滚动”的开关**：违背了移动端“直观无感”的交互原则，增加了用户的心智负担。

## Consequences
- **移动端体验达到原生 App 级别**：手指按住屏幕，视线停留在哪，页面就绝对不动如山。
- **牺牲了“全自动看最新回复”的便利性**：用户在发消息后，如果需要看新回复，必须自己手动滑下去，或点一下红点徽章。
- 彻底解决了流式高频重排引发的浏览器卡顿与页面乱跳问题。
